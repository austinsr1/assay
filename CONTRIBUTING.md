# Contributing

This file exists because a contributor agent once could not find the setup
instructions: they lived in a gitignored directory on the build host, so no clone
anywhere else could see them. Anything a contributor needs is tracked here instead.

Read this before your first commit. Two of the rules below are permanent if
broken, and neither produces an error at the time.

---

## Before anything else: set your commit identity

```bash
git config user.name  "Your Name"
git config user.email "you@example.com"
```

**This is mandatory, not advisory, and it is repo-local on purpose.**

A fresh clone inherits whatever global identity the host happens to have — often a
machine or migration account belonging to whoever provisioned the host. If you commit
without overriding it, your work is attributed to that identity. Check both fields,
not just the name: a host can have a sensible global `user.name` and an internal
domain in `user.email`, and it is the email that ends up published. An agent that
sets its own identity should set a real name and a real address, not a bare machine
label.

It cannot be fixed afterwards. The shared repository sets
`receive.denyNonFastForwards = true`, which blocks the history rewrite that would
correct attribution, and this project is destined for a public exchange whose review
scans the **full git history**. Verify before your first commit:

```bash
git config user.email    # must be yours, not the host's global value
```

## Getting set up

```bash
git clone <shared-repo-url> tenable-email-<topic>
cd tenable-email-<topic>

git config user.name  "Your Name"
git config user.email "you@example.com"

python3 -m venv .venv                 # Python 3.10 or newer; see below
.venv/bin/pip install -e ".[test]"
```

`pyproject.toml` declares `requires-python = ">=3.10"`. Hosts often have an older
system `python3` alongside a newer `python3.12`; check with `python3 -V` and use the
supported one. The suite has been seen to run on 3.9, but that is below the declared
floor and is not a supported configuration.

### Running the tests

```bash
python3 -m pytest tests/ -o addopts= -q
```

**The `-o addopts=` is required.** `pyproject.toml` sets `addopts = "-q"`, and
stacking a second `-q` suppresses the summary line, so you get no totals and no
failure list. This has wasted time more than once.

Expected on a clean tree: zero failures, zero unexpected skips, and an xfail count
matching the number of declared-open findings. Both xfails are `strict`, meaning
**fixing one turns the build red** until the expectation is consciously updated.
That is deliberate — see "Declared-open findings" below.

## Branches and pushing

Work on a branch named `<you>/<short-topic>` and never push to `main`:

```bash
git checkout -b yourname/google-intake
git push -u origin yourname/google-intake
```

Merging to `main` is a single-writer operation. Two writers pushing `main` collide,
and with non-fast-forward pushes rejected the second one gets:

```
! [rejected]  main -> main (non-fast-forward)
```

That is the guard working. Recover with `git pull --rebase origin main`.
**Never `--force`.** An agent that responds to a rejected push by forcing will
destroy someone else's work, so say explicitly in its instructions not to.

## Four rules that cause silent damage

### 1. Do not re-record the evidence artifacts on a branch

`docs/results/latest.md` and `docs/results/junit.xml` are generated by
`tools/record-results.sh` and describe the tree they were run against. If your branch
re-records them and `main` has also moved, the merge conflicts on both files — and
the conflict is unavoidable, because the artifact from either parent is wrong for
the merged tree.

Leave them alone on your branch. Whoever merges re-records them once, against the
merged tree, so the evidence describes something that actually exists.

If you do need to record, resolve the conflict by **deleting both files and
re-running the script** — never by hand-editing or picking a side.

Never pipe the script into `tail` or any other command. A pipe replaces its exit
status, defeats `set -e`, and a red artifact gets committed as if it were green.
That has happened.

### 2. Sync from `main` before you record or before you judge a failure

A branch that forked days ago inherits whatever was broken at the fork point. One
contributor branch recorded 35 test failures that were **entirely** inherited from
its fork point — every one of them already fixed on `main` — and the failures looked
like the new code's fault. They were not.

```bash
git fetch origin
git rebase origin/main        # or merge; rebase keeps the branch readable
```

Then re-run the suite and only investigate failures that remain.

### 3. A commit message must not imply a pass that did not happen

Recording evidence honestly is required and good — an artifact that says
`Exit code 1` with a failure count is far better than a fabricated green one. But
the **commit subject** must not read like a pass. "record the suite at 734 tests"
states a collected count and reads as success; the artifact it committed recorded 35
failures.

Say what happened: `test: record the suite red - 35 inherited failures from fork
point`, or better, fix the fork point first and record green.

The project's own operating rule is that the suite passes before a commit. If you
must commit a red tree, the subject has to say so.

### 4. Anything that mutates must go through the approval gate

This project's safety model is propose → approve → execute, and it is the reason a
verdict cannot silently change somebody's mailbox. Every mutating stage declares
human approval in `stages.yaml`, and `src/tenable_email/runner.py` enforces
single-use approval tokens bound to the verdict digest they were granted against.

A transport client exposing `create_label` or `modify_labels` is fine — that is just
an API surface. But it must not become reachable from the pipeline, the CLI or an
MCP tool except through a `WritebackProvider` with `mutates = True` whose `execute()`
runs only against a validated `Approval`.

If your change adds a way to mutate, wire it through the gate in the same change. A
provider that reports an action as performed when it was not is the exact failure the
contract exists to prevent: return `performed = False` with a detail naming the
reason instead.

## Declared-open findings

Known-broken behaviour is asserted with a **strict** xfail:

```python
@pytest.mark.xfail(strict=True, reason="what is wrong, and what closing it needs")
def test_the_known_open_case():
    ...
```

Strict means the test fails the build the day it starts passing, forcing a conscious
status update rather than a silent one. When you fix one of these, the build goes red
until you move the expectation — that is the mechanism working, not a regression.
Update the status in `docs/RED-TEAM-RESPONSE.md` in the same commit.

## Publication boundary

This repository is destined to be public and is scanned in full history. Do not
commit:

- Real mail, real employee addresses, live alert data, or credentials. Fixtures are
  synthetic and use RFC 2606 reserved domains (`.test`, `.example`, `.invalid`).
- Private infrastructure in any tracked public-bound file: internal hostnames, IP
  addresses, service paths, tunnel configuration, web roots, ssh remotes, or
  colleague names.

`tests/test_doc_references.py` enforces this and fails the build on a match. Note one
weakness in a fresh clone: the generic patterns live in the test file, but the
organization-specific term list loads from a gitignored file, so **a clone runs the
generic checks and silently skips the org-specific ones**. Ask the maintainers for
the terms file, or run the suite in the build tree, before trusting a clean result
from a fresh clone.

Two traps worth knowing:

- A **generated corpus needs its own `.gitignore` negation.** `*.eml` is ignored so
  real mail can never be committed; each synthetic corpus directory needs an
  explicit `!path/*.eml`. A second corpus was once generated and never committed —
  the suite passed locally because the files were on disk, while every fresh clone
  collected `FileNotFoundError`. A manifest-derived guard now fails the build if a
  corpus file is untracked.
- A guard's own pattern list can match itself. If you add a tool that scans for
  forbidden strings, **import the pattern list from the module that owns it** rather
  than restating it, or the tool trips its own guard.

## House conventions worth following

- `dependencies` in `pyproject.toml` stays **empty**. Runtime is standard library
  only; optional capability goes in an extra, and an extra must actually change
  behaviour — a documented `pip install .[extra]` that resolves to nothing is worse
  than no extra.
- Model tiers return failure **as a value** (`available=True, ok=False, reason=...`),
  never as an exception, so an unconfigured tier records `UNAVAILABLE` instead of
  crashing the chain. No endpoint has a default anywhere.
- Evidence carries provenance — `VERIFIED`, `MODEL_JUDGMENT`, `UNKNOWN`,
  `UNAVAILABLE` — and a verdict may not cite a finding whose provenance does not
  support it. `UNKNOWN` is distinct from absent.
- Absence of evidence cannot be filled by model confidence. A truncated message, an
  unparsed part, an unread attachment or an unexamined image cannot be cleared by a
  unanimous model vote; a judgment about content that *was* read can be.
- Comments and docstrings must describe what the code actually does. Several findings
  in review were prose overstating the code. If you are unsure whether something
  works, run it.
- Prefer pinning the **policy** to pinning the implementation: a corpus-level
  assertion that no hostile case auto-clears survives refactors, and catches the
  next bypass nobody thought of.

## Getting a branch merged

Tell the maintainers the branch name and:

1. What it does, in one paragraph.
2. The real output of `python3 -m pytest tests/ -o addopts= -q` on the merged-with-`main` tree.
3. Anything unfinished, explicitly. A partial branch with an honest gap list is far
   more useful than one claimed complete.
4. Whether anything you added can mutate state, and where the approval gate is.

A maintainer re-runs the suite on the merged tree, re-records the evidence once, and
merges. Verified recently: a two-commit branch adding ~1,160 lines of client code and
~690 lines of tests merged with conflicts only in the two evidence artifacts, and the
merged tree ran green.
